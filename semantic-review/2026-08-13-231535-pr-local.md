# Patient sidebar visibility and permission backfill

This change moves the patient navigation and pages to the canonical `/pazienti` surface, derives visibility from the active operational context, and adds patient invitations alongside the existing relationship APIs. The database side introduces the invitation type split, backfills patient permissions for existing organization roles, and replaces ambiguous SQL function definitions with lint-clean versions. Organization permissions come from the selected membership, while personal-professional access is gated separately by professional readiness. **Watch for:** **[confirmed]** the permission backfill test is not executed by the configured backend suite; **[confirmed]** the new migrations are untracked and absent from `git diff main`; **[likely]** a stale database can mark the backfill successful while silently inserting no role mappings because the migration does not assert that its target roles exist.

## High-level view

The sidebar and patient routes use the active context’s `operationalPermissions`; **[confirmed]** an organization practitioner is denied patient access despite active membership, while an operational personal-professional context receives its separate patient capability set. **[confirmed]** The organization ID passed to patient RPCs comes from that authenticated context rather than page input.

The permission repair is additive and mostly idempotent through `ON CONFLICT`, and the invitation/history functions separate organization-member records from patient records. **[confirmed]** The main deployment risk is that the SQL files are untracked and the Supabase CLI cannot inspect migration state in this unlinked checkout; **[likely]** the backfill can also complete without creating all intended mappings.

### Active-context permission derivation and practitioner boundary

**[confirmed]** `getAuthorizationContext` computes organization permissions only from `member_roles` belonging to the selected membership and filters those assignments to organization-scoped roles. Context resolution uses canonical memberships and owned professional profiles, and the patient page/API checks `patients.read` again before accessing an organization- or professional-scoped RPC. This is the correct shape for preventing a browser-provided organization or membership identifier from selecting another organization; the missing proof is executable permission-mapping coverage.

**[confirmed]** The backfill grants `patients.read` to `organization_owner`, `organization_admin`, `clinical_director`, and `office_manager`, but not `practitioner`, `staff`, or `finance`. The personal-professional branch separately receives `patients.read`, `patients.link`, and `patients.unlink` when operational; `patients.invite` is not added there, so invitation remains organization-only.

**[confirmed]** The current executable tests cover context enumeration, stale-context fallback, navigation visibility, and the patient invitation service, but not the database-to-`operationalPermissions` mapping. `apps/backend/src/__tests__/db/patient-permissions-schema.test.ts` is outside `vitest.canonical.config.ts`’s `src/__tests__/db/foundation-schema.test.ts` include, so its source-text assertions do not run under the workspace backend test command. Add behavior-level coverage proving that an organization practitioner lacks `patients.read`, allowed roles have it, and a user can select organization B only with an active membership and role assignment there.

### Organization scope and patient route behavior

**[confirmed]** `/pazienti` and `/pazienti/[id]` require an active operational context and `patients.read`; the backend derives both the RPC name and scope ID from that context. The detail RPC receives the organization ID or professional profile ID, so a relationship ID from another context is not sufficient to retrieve data. The legacy `/clienti` routes redirect to the canonical paths instead of maintaining a second authorization implementation.

**[likely]** The SQL backfill is idempotent for rows it can resolve: permission upserts and role-permission inserts use `ON CONFLICT`. It is not self-validating. Inner joins against `roles` and `permissions` allow a stale schema with a missing role or permission to finish with fewer mappings and leave the sidebar hidden without a migration error. Add an expected mapping-count assertion or fail when a required role code is absent, then execute the resulting authorization query in a representative schema test.

### Migration chain, stale local state, and SQL corrections

**[confirmed]** `20260813000400` follows the canonical invitation/history columns it uses and splits the old pending-email uniqueness rule into member and patient rules. `20260813000500`, `20260813000600`, and `20260813000800` are data-operation-idempotent through permission upserts and conflict-safe mapping inserts. The schema/function migrations are one-shot rather than blindly rerunnable: the new column, constraints, and indexes in `20260813000400` lack `IF NOT EXISTS`, so a partially recorded migration requires state inspection before replay.

**[confirmed]** The six new migrations are untracked, so `git diff main` reports none of them. That matters to the stale Supabase diagnosis: an application-only patch can show the sidebar change while omitting the database fix. `supabase migration list` could not verify state because this checkout is not linked to a Supabase project; include the migrations in delivery and run a local reset or linked migration-status check before concluding that missing `patients.read` rows are fixed.

**[confirmed]** `20260813000900_fix_sql_lint_ambiguities.sql` replaces the catalog import function with distinct incoming-code names and qualifies the invitation revoke query. The historical catalog migration still contains the original definition and relies on this corrective migration being applied, so lint/build validation must run against the complete migration chain rather than only inspect the final file.

### Invitation isolation relevant to the patient surface

**[confirmed]** Organization invite queries, expiration, list, revoke, resend, and token lookup now filter `invitation_type = 'organization_member'`; patient operations use the opposite type and a dedicated service-role RPC. Acceptance creates or reactivates only an `organization_patient_relationships` row and checks the current user’s email against the invitation email, so the patient flow does not create organization membership.

**[possible]** The database backfill and invitation migrations are validated primarily by source-text assertions and service mocks. A local database execution should cover the unique-index split, repeated backfill application, member-history exclusion, patient acceptance/reactivation, and member-token rejection on the patient route; without it, grants, RLS, SQL syntax, and function behavior remain less verified than the TypeScript paths.
